# Campaign Autopilot — 캠페인 일괄 구체화·일괄 실행

**유저 개입을 셋으로 줄이는 모드다** — 질문 라운드 한 번, 일괄 승인 한 번, 최종 PR 리뷰. 기본 흐름은 DP 마다 지침을 쓰고 승인받아, 그때마다 유저가 멈춰 서야 한다. 이 모드는 전 DP 를 미리 구체화해 한 번에 승인받고, 구현은 서브에이전트로 끝까지 이어간다.

## 0. 기존 스킬과의 관계

이 스킬은 opord·orchestrate 를 부품으로 쓴다. 지침은 opord 로 쓰고 구현은 orchestrate 로 실행한다. opord·orchestrate·campaign 은 이 스킬을 모른다 — 이 모드에서 달라지는 읽기는 전부 여기에 적는다. 세 스킬 조항은 아래 네 자리만 빼고 그대로 따른다.

- **opord §3-2 착수 자격은 지침을 쓸 때와 브랜치를 딸 때로 나눠 읽는다.** 지침을 쓸 때는 "선행 DP 머지" 를 campaign.md 8항 인터페이스 계약 확정이 갈음한다 (§2-2). 브랜치를 딸 때는 선행 DP 의 PR 이 넘어가는 신호(§3-3-4)를 받았어야 한다.
- **opord §3-8 의 DP 별 승인을 일괄 승인 하나가 갈음한다** (§2-6). 승인 요약 서식·plan-review 관문·착수 확인 봇 코멘트는 DP 마다 그대로 돈다. 유저에게 묻는 자리만 하나로 모은다.
- **orchestrate §2 의 stacked 명시 허용은 일괄 승인 문서의 허가 항목으로 받는다.** 그래서 선행 DP 의 PR 이 넘어가는 신호(§3-3-4)를 받으면 머지를 기다리지 않고 그 브랜치를 base 로 다음 DP 를 딴다.
- **campaign 평가 모드는 DP PR 마다 그대로 돌되, 다음 DP 선택(campaign §4-8)과 DP 경계의 `/clear` 청구(campaign §5)는 승인 문서의 실행 배치와 §3 DP 루프가 갈음한다.** MOP·MOE·가정 검증·원장 갱신은 그대로 한다.

통제 세션이 있는 캠페인이면 관문 셋(plan-review·PR 리뷰·보고 검수)은 이 모드에서도 전부 돈다. 줄이는 것은 유저 승인이지 관문이 아니다.

## 1. 진입

- campaign.md 가 승인됐고 유저가 이 모드로 가라고 지시했을 때만 시작한다. 발동하면 먼저 상위 이슈 원장의 런 줄을 본다 — 없으면 §2 처음부터, `계획` 이면 원장과 지침 파일로 어디까지 왔는지 확인해 §2 를 잇고, `승인 대기` 면 §2-6 승인 처리로, `실행` 이면 §3, `리뷰 대기` 면 §5 로 들어간다. 캠페인 계획을 쓰는 중이면 campaign 스킬이 먼저다.
- 대상은 campaign.md 9항의 DP 전부다. 결정지점 뒤로 미뤄 둔 조건부 DP 는 빼고, 승인 문서의 "이번 런 밖" 줄에 적는다.
- **런 줄** — 캠페인 원장(`.operations/<상위이슈>/campaign-progress.md`) 하단 세션 장부 첫 줄에 `campaign-autopilot: <단계> — <대상 DP 목록>` 을 둔다. 단계는 `계획` → `승인 대기` → `실행` → `리뷰 대기` → `종료` 로 바꾼다. 원장이 이슈 미러에 실리므로 `/clear` 뒤 세션은 이 줄에서 런을 찾는다.

## 2. 계획 단계

1. **DP 이슈 일괄 생성** — 런 줄을 `계획` 으로 만든다. 대상 DP 이슈를 issue 스킬로 전부 만들고 원장을 `착수` 로 올린다.
2. **DP 별 사전 조사** — opord §3-3 대로 한다. 선행 DP 의 산출물이 아직 코드에 없으면 campaign.md 8항 인터페이스 계약을 사실로 놓고, 그 지침의 1-라 가정 표에 `선행 DP 계약 기준` 으로 적는다.
3. **질문 라운드 한 번** — 전 DP 의 "묻는 것"(opord §3-5)을 모아 한 라운드로 묻는다. 앞 DP 의 답이 뒤 DP 의 질문을 바꾸면 같은 라운드 안에서 묶어 묻는다. **예외 상황과 가정이 깨졌을 때의 대응은 여기서 구체화하지 않는다.** 지침의 결정지점·예외 대응 표에는 기본 행동 "그 체인을 멈추고 긴급 보고한다" 하나를 둔다.
4. **지침 작성** — DP 마다 opord §3-4·§3-6·§3-7 대로 쓴다. 파일은 조율 세션(§3-2) 워크트리의 `docs/operations/<DP이슈>/opord-<DP>.md` 다. 다른 세션이 맡을 DP 도 여기에 두고, 그 세션은 절대 경로로 읽는다. 지침은 **실행 세션이 유저에게 다시 묻지 않고 구현할 수 있을 만큼** 결정을 담는다.
5. **plan-review** — 통제 세션이 있으면 지침마다 그 세션의 1차 리뷰를 받는다. 건별 허가도 이때 함께 받는다. 반려된 지침만 고쳐 다시 받는다.
6. **일괄 승인** — 승인 문서 `docs/operations/<상위이슈>/run-approval.md` 를 쓰고, 통제 세션이 있으면 보고 검수를 거쳐 유저에게 올린다. 올리면서 런 줄을 `승인 대기` 로 바꾼다. 항목은 다섯이다.
   - 런 요지 — 대상 DP, 이번 런 밖 DP, 끝났을 때의 결과물, 1차 리뷰 결과(plan-review 를 통과시킨 세션 이름 또는 "지정 없음" — 유저 지시와 strategy.md 통제 세션 줄을 보고 적는다)
   - DP 별 승인 요약 — opord 승인 요약 서식의 1~3 블록을 DP 마다
   - 실행 배치 — 세션별 DP 배정, 병렬 묶음, stacked 체인 순서
   - 허가 — stacked 진행 허가, 통제 세션이 내준 건별 허가 목록
   - 유저 검증 대기 예정 — 실기·계정이 필요해 PR 본문으로 넘길 항목

   유저가 승인하면 DP 마다 opord §6·§7 대로 명령 상태를 `재가` 로 올리고 원문을 게시·미러한다. 유저가 일부 DP 만 고치라고 하면 그 지침만 고쳐 plan-review 를 다시 받고 승인 문서를 다시 올린다.
7. **실행 준비** — 런 줄을 `실행` 으로 바꾸고 세션 배정(`배정 <세션>: <DP 목록> / …`)을 같은 줄에 붙인다. 유저에게 `/clear` 뒤 `/campaign-autopilot <상위이슈>` 를 치라고 명령 그대로 안내한다. 보조 세션이 있으면 그 세션에 배정과 지침 경로, 같은 재개 명령을 보낸다.

## 3. 실행 단계

1. **복원** — `/clear` 뒤에는 상위 이슈 미러의 런 줄과 각 지침 파일에서 상태를 되살린다. 대화 기억에 기대지 않는다.
2. **조율 세션** — 캠페인 주 세션(campaign.md 13항 `주 작업 자원` 칸의 세션)이 조율한다. 보조 세션 배정·체인 rebase 지시·원장 갱신이 조율 세션 몫이다. 세션이 하나면 그 세션이 조율하고 순서대로 실행한다.
3. **DP 루프** — 각 세션은 자기 DP 를 orchestrate 로 실행한다. 세션은 서브에이전트를 통제하고 코드를 직접 만지지 않는다. DP 하나마다 이 순서다.
   1. 브랜치를 base(선행 DP 가 없으면 develop, 있으면 그 브랜치)에서 딴다.
   2. 지침대로 서브에이전트가 구현한다. 브리프는 orchestrate §4-2 다.
   3. PR 직전 whole-branch 리뷰(implement §착수)를 돌리고, PR 문안 검수를 거쳐 PR 을 올린다.
   4. **넘어가는 신호를 받을 때까지 다음 DP 로 넘어가지 않는다.** 통제 세션이 있으면 PR 리뷰 통과가 신호다 — 지적은 원본 커밋에 흡수하고 다시 받는다. 통제 세션이 없으면 3 의 whole-branch 리뷰 통과가 신호를 갈음한다.
   5. 신호를 받으면 원장을 갱신한다. 보조 세션이 낸 DP 면 조율 세션에 알리고, 조율 세션은 그 DP 를 선행으로 둔 DP 를 착수시킨다.
4. **예외** — 지침의 결정지점·예외 대응이 발동하거나, 가정이 깨지거나, 지침이 덮지 않는 상황(implement 플랜 갭)을 만나면 그 DP 와 그 위에 쌓인 체인을 멈춘다. 긴급 보고(`report-immediate.md`)를 상위 이슈에 게시하고 유저 결정을 기다린다. 통제 세션이 있으면 유저에게 내는 메시지는 보고 검수를 거친다. 의존이 없는 다른 체인은 계속 간다.
5. **컨텍스트** — 세션이 diff 와 보고 전문을 컨텍스트에 싣지 않는 것은 orchestrate 원칙 그대로다. DP 경계에서 세션을 비워야 하면 런 줄로 복원한다.

## 4. 완료 보고

대상 DP 의 PR 이 전부 넘어가는 신호(§3-3-4)를 받으면 유저에게 완료 보고를 한 번 올리고 기다린다. 통제 세션이 있으면 보고는 보고 검수를 거친다. 실을 것은 PR 목록과 머지 순서(stacked 체인 순서), 유저 검증 대기 항목, 이번 런 밖으로 남은 DP 다. 리뷰 반영은 `/campaign-autopilot <상위이슈>` 로 부르라고 함께 적는다. 런 줄은 `리뷰 대기` 로 바꾼다.

## 5. 리뷰 단계

- 유저가 중간 PR 에 지적을 달면 그 DP 를 맡은 세션이 지침 범위 안에서 원본 커밋에 흡수한다. 지침 범위를 넘는 지적이면 opord §6 변경 지시로 기록한다.
- 고친 PR 위에 쌓인 PR 들은 체인 순서대로 rebase 하고 테스트를 다시 돌린다 (orchestrate §5). 조율 세션이 순서를 지시한다.
- 통제 세션이 있으면 고친 PR 은 그 세션의 재리뷰를 받는다. rebase 만 한 PR 은 충돌을 푼 자리가 있을 때만 재리뷰를 받는다.
- 머지는 유저 승인 뒤 체인 앞부터 한다. 머지 뒤 처리는 pr 스킬 머지·정리와 orchestrate §5 다.

## 6. 종료 기록 — skill_end

런당 한 번이다. 대상 DP 가 전부 머지되거나 유저가 런을 접으면, 런 줄을 `종료` 로 바꾸고 `python3 .claude/hooks/log-record.py skill_end --name campaign-autopilot` 을 기록한다 (명령·compliance 규칙은 CLAUDE.md §1). 기록 주체는 런 줄을 보고 마지막 머지를 처리한 세션이다. 그 안에서 발동한 opord·orchestrate·implement 는 각자 자기 종료 조항대로 기록한다.
