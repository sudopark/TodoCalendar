# 파일 공통 관례

## 1. 파일 헤더 템플릿

새 Swift 파일 상단 주석은 최신형(Copyright 포함)으로:

```swift
//
//  <FileName>.swift
//  <TargetName>
//
//  Created by sudo.park on <M/d/yy>.
//  Copyright © <yyyy> com.sudo.park. All rights reserved.
//
```

- 2번째 유의미 줄 = 파일명, 3번째 = 소속 타겟(프레임워크)명 (`Domain` / `Repository` / `SettingScene` 등). 테스트 파일도 동일 형식.
- 구형(2023년식, Copyright 없는 형식)이 코드베이스에 혼재하나 새 파일은 최신형으로. 기존 파일 헤더 일괄 수정 금지.

## 2. import 순서

표준 라이브러리 → 렌즈 → 하위 레이어 → 공유 인터페이스 → 공용 UI 순:

```swift
import Foundation   // 또는 UIKit / SwiftUI
import Combine
import Prelude
import Optics
import EventDomainInterface
import SceneInfra
import EventDetailSceneInterface
import CommonPresentation
```

필요한 것만 import — 위 순서에서 해당 없는 줄은 생략.

## 3. 새 기능의 배치 — 기존 확장이 기본값

새 능력은 **이미 그 책임을 가진 타입에 메서드·case·필드를 더해서** 넣는다. 같은 서브도메인·같은 데이터 소스·같은 소비자를 가진 기존 Usecase·Repository·Service·ViewModel 이 있으면 그 타입을 넓힌다. 새 타입·프로토콜·파일은 아래 셋 중 하나를 댈 수 있을 때만 만든다. **근거는 주장으로 적지 않는다** — 기존 자리에 녹인 안을 한 줄로 쓰고, 그 안이 실패하는 구체 지점(의존 방향 역전·모듈 경계·소비자 둘의 계약 상충)을 적는다. 실패 지점은 이름만 대지 않는다 — 어느 타입이 어느 타입을 알게 되는지(또는 어느 계약이 어떻게 상충하는지)를 한 문장으로 쓰고, 깨지는 의존·호출 경로를 `파일:줄` 로 댄다. "문구가 달라서"·"기능이 달라서"·"역할이 다르니까"는 실패 지점이 아니다 — 값·파라미터로 담긴다. 실패 지점을 못 적으면 녹임 안이 답이다 (#1268 — 신설물마다 근거 문장은 있었지만 녹임 안을 그려 본 것은 없었고, 유저 리뷰에서 아홉 건 전부 녹임 안으로 되돌아갔다):

1. **직접 연결이 불가하다** — 기존 타입에 넣으면 의존 방향이 뒤집히거나(하위 레이어가 상위를 앎), 모듈 경계를 넘는다.
2. **소비자가 지금 둘 이상이다** — 추상은 두 번째 소비자가 생길 때 도입한다. 소비자가 하나뿐인 프로토콜·래퍼·중간층은 만들지 않는다.
3. **관심사가 실제로 독립이다** — 서브도메인이 다르거나(`docs/domain-context-map.md`), 세만틱이 다르다. 이벤트 성격의 신호(`PassthroughSubject` — 팝업 트리거)와 상태 성격의 값(`CurrentValueSubject` — 조회 가능한 현재 값)은 한 source 로 합치지 않는다.

위 근거가 서 보여도 **바이패스 객체는 만들지 않는다** — 모든 멤버가 받은 것을 다른 객체에 넘기기만 하는 타입(위임 한 줄 어댑터·스냅샷 소스 류)은 판단·변환·상태를 보태지 않아 경계가 아니고, 테스트 더블·조립 코드·따라갈 간접층만 늘린다. 근거 1(직접 연결 불가)이 실제로 성립해 기존 타입이 그 계약을 직접 채택할 수 없는 자리의 경계 구현체는 바이패스가 아니다 — 기존 타입이 직접 채택할 수 있는데 타겟·빌드 사정(@testable 재컴파일로 채택이 중복되는 류)이 가로막은 것은 성립이 아니니, 그 사정은 타겟 구성·채택 위치 쪽에서 먼저 풀고, 못 풀면 유저에게 보고한다 — 어댑터 신설로 우회하지 않는다 (#1262 `BillingUserPlanSnapshotSource` 반려. implement 리팩터 게이트의 흐름 은폐가 같은 기준으로 함수를 본다).

**분할·공용화·상태 도입도 같은 판정 대상이다** — 새 타입이 아니어도 아래 셋은 같은 과설계라 같은 형식(녹임 안 + 실패 지점)으로 판정한다:

- **변주는 값으로 담는다** — 같은 terminal 동작으로 끝나는 사용처들의 차이(문구·정책값·아이콘)는 타입·case·프로토콜 분할이 아니라 연관값·파라미터로 담는다. 분할은 소비자가 계약 자체를 다르게 소비할 때만 하고, 그 차이도 주장이 아니라 실패 지점으로 적는다 — 어느 소비자의 어느 호출이 한 계약으로 안 담기는지 (#1268 사유 enum 의 적용/생성 분할·기능별 하위 게이트 프로토콜 셋 반려 — 검사 하나와 feature 값으로 합쳐졌다).
- **공용화는 상속이 아니라 조립이다** — 화면·컴포넌트 재사용을 open class 상속 + override 조회로 풀지 않는다. 공용부를 독립 씬·타입으로 세우고 빌더 조립으로 잇는다. `BaseRouterImple` 처럼 전 Router 가 쓰는 기반 클래스와 OS·SDK 가 요구하는 서브클래싱(UIKit 뷰·셀·컨트롤러)은 대상이 아니다 (#1268 open 시트 Router 상속 반려 — 시트 전용 Router 를 그 모듈 안에 두고 화면 Router 는 빌더 하나만 받는 형태로 바뀌었다).
- **일회 상태 대신 재검사** — 검사 결과를 저장해 다음 검사를 건너뛰게 하는 통과권·일회 플래그가 대상이다. 흐름이 돌아오면 같은 검사를 다시 돌린다. 저장된 통과 상태는 소비·초기화 시점 결함을 만들고 테스트 조합을 늘린다. 서버·OS 가 소유한 값의 캐시·토큰이나 상태 성격의 현재 값(`CurrentValueSubject`)은 대상이 아니다 — 검사를 우회하는 게 아니라 값 자체다 (#1268 일회 통과권 반려).

신설 전에 셋을 먼저 확인한다:

- **같은 구분이 이미 모델링돼 있나** — 결정·상태를 담을 enum 을 새로 세우기 전에 같은 구분을 드는 기존 enum·Bool·에러 타입을 grep 한다. 이번 작업의 스코프 안에서만 보면 바로 옆의 결정 타입을 못 본다 (#1257 의 `PendingIntent` 가 결국 `RewardedAdLicenseDecision` 으로 통합된 자리). 소비 분기가 한 곳뿐이면 enum 없이 그 자리의 분기로 끝낸다.
- **값이 이미 흐르고 있나** — "이 시점에 값이 없다"면 새 상태·상태기계를 만들기 전에 그 값의 출처를 역추적한다. 대개 응답이나 기존 필드에 이미 있고, 소비자까지 안 오는 것뿐이다. 안 오는 이유가 타입의 표현력 부족이면(두 단계를 한 타입으로 방출) 상태가 아니라 타입을 모델링한다 — enum case 로 단계를 드러내면 소유는 기존 자리에 그대로 둔다.
- **경계를 현재 시그니처로 판정하지 않았나** — 레이어 배치는 지금 인터페이스 형태가 아니라 소비자가 어쩔 수 없이 지정해야 하는 최소 어휘(대개 "어느 것" 하나)로 판정한다. 나머지 값을 구현체가 스스로 만들 수 있으면 인터페이스를 좁힌다. OS·SDK 스펙에 묶인 타입(`Codable`, `ActivityAttributes` 등)은 그 요건을 지는 구현체 쪽에 둔다.

**신설 타입·메서드 이름은 레퍼런스를 댄다** — 프로젝트가 이미 쓰는 이름 패턴(CLAUDE.md §5 네이밍 표·동종 컴포넌트 grep), GoF·일반 디자인 패턴 이름, 도메인 용어(`docs/domain-context-map.md`) 중 하나에 닿아야 하고, 레퍼런스엔 닿은 대상(기존 타입 이름 또는 패턴 이름)을 적는다. **닿았다는 판정은 접미사 일치가 아니라 책임 일치다** — `GoogleCalendarEventColorResolver` 가 있다는 사실이 다른 책임의 `XxxResolver` 를 세워 주지 않는다. 어디에도 안 닿는 이름은 이름 문제가 아니라 배치 문제다 — 책임이 안 선 자리라 이름이 안 서는 것이니, 이름을 다듬지 말고 배치 판정으로 돌아간다 (#1262 `WidgetStyleResolver` 반려). 이름에 `resolve`·`perform`·`execute`·`settle` 같은 범용 동사가 들어가면 같은 신호다 — 처리 케이스를 이름에 박지 못해 동사만 남은 것이라, 그 타입·메서드의 설계부터 다시 본다. 프로토콜·시스템 API 가 강제하는 이름(AppIntents 의 `perform()` 류)은 신호 대상이 아니다.

**Why:** 신설은 파일·프로토콜·Imple·테스트 더블·조립 코드를 한꺼번에 늘리고, 읽는 사람이 따라갈 간접층을 남긴다. 소비자 하나뿐인 추상은 리팩터 게이트의 Speculative Generality 에도 안 걸린다.

## 4. extension 배치 — 같은 파일 안 `// MARK: -` 가 기본값

extension 은 대상 타입의 파일, 또는 그 extension 을 쓰는 파일 안에 `// MARK: -` 블록으로 둔다. `Type+Xxx.swift` 별도 파일은 아래 셋 중 하나일 때만 만든다:

1. **다른 파일 둘 이상이 쓴다** — 범용이면 `Extensions` 모듈, 모듈 내부 공용이면 그 모듈의 공용 위치로 간다.
2. **룰이 분리를 규정한다** — `Xxx+Mapping.swift`(repository-rules §2), Scene 6파일(presentations-rules §3), `Scenes+*.swift`(presentations-rules §7).
3. **채택 타겟이 대상 타입과 다르다** — 앱 타겟이 ServiceInterfaces 프로토콜을 채택하는 extension 처럼 대상 타입 파일에 둘 수 없는 경우.

**Why:** 파일을 떼면 `private` 헬퍼가 `internal` 로 넓어지고(testability §3), 파일이 늘어 찾고 따라가는 비용만 커진다. 위 `+Mapping`·`Scenes+` 이름은 규정이 있어 뗀 선례라 일반 관례로 따라 하지 않는다.
